# Reproducibility checklist — PIER

**Owner:** Elias (`feat/docs-entrega` + `feat/entrega-produccion`)
**Purpose:** Make any demo or production claim traceable to a concrete run, without video, slides, or presentation polish.

---

## 1. Deterministic demo

A stranger can clone the repo and get the same demo result:

```bash
git clone <repo> pier-spaceapps
cd pier-spaceapps
python -m pip install -r requirements.txt
python -m piper_agent.data.generate_cache
python -m piper_agent --lat 41.8 --lon -93.6 --date 2025-05-15 --demo --demo-name flood
```

Default mode is demo (`PIER_DEMO_MODE=1`). No credentials required.

---

## 2. Cache version

- Synthetic cache lives under `piper_agent/data/cache/` and `piper_agent/data/baselines/`.
- The cache is regenerated by `python -m piper_agent.data.generate_cache`.
- The same generator and fixed seeds produce the same cache on every clean run.
- Cache is gitignored. If a result is reproduced from cache, record which generator
  commit produced it (the cache is a derived artifact, not a source of truth).

---

## 3. Contract version

- The contract is the code in this repo at run time.
- `run_pier(...)` and `load_demo_packet(...)` are the stable integration points.
- New contract keys are read downstream with `.get()`, so the output shape stays
  stable as keys are added.
- The exact set of keys present in a run can be reproduced by checking out the
  same commit and running the same scenario.

---

## 4. Production path

- The production (live-data) path is opt-in only and activated by setting
  `PIER_DEMO_MODE=0` and providing the relevant credentials.
- Live-data results are reproducible only when the same credentials, same
  endpoints, and same circuit-breaker state are used.
- If any live service is unavailable, the pipeline falls back to synthetic cache
  and labels the result `fuente_datos="sintetico"`.
- The `fuente_datos` label in every output is the production-path provenance
  record: it says whether the run used synthetic cache, NASA POWER, or POWER+IMERG.

---

## 5. What to record for a claim

For any claim made about a run, record:

- Repository commit used
- `PIER_DEMO_MODE` value
- Scenario / lat / lon / date
- `fuente_datos`
- Whether the cache was regenerated before the run
- Whether any live credential was set
- Any circuit-breaker fallback that occurred
